## `actaflow.cases.v1`

### Service `AttachmentService`

Encrypted attachments of a case (identity documents, contracts, evidence).

Files are encrypted in a browser Web Worker before upload. The BFF runs on Vercel, whose
functions accept at most 4.5 MB per request, so files travel in chunks of up to 3 MB.

| RPC | Request | Response | Description |
|---|---|---|---|
| `BeginAttachmentUpload` | `BeginAttachmentUploadRequest` | `BeginAttachmentUploadResponse` | Registers a new attachment and returns where to send its chunks. Errors: RESOURCE_EXHAUSTED (case storage quota of the free plan reached). |
| `UploadAttachmentChunk` | `UploadAttachmentChunkRequest` | `UploadAttachmentChunkResponse` | Uploads one encrypted chunk. Re-sending the same chunk index is idempotent. |
| `CompleteAttachmentUpload` | `CompleteAttachmentUploadRequest` | `CompleteAttachmentUploadResponse` | Marks the upload complete after checking that every chunk arrived. |
| `ListAttachments` | `ListAttachmentsRequest` | `ListAttachmentsResponse` | Lists the attachments of a case. |
| `GetAttachmentChunk` | `GetAttachmentChunkRequest` | `GetAttachmentChunkResponse` | Downloads one encrypted chunk. |
| `DeleteAttachment` | `DeleteAttachmentRequest` | `DeleteAttachmentResponse` | Deletes an attachment. Only its uploader or a conciliator. |

### Service `CaseService`

Case files (expedientes). Implemented by legal-case-service.

Access rule for every RPC: the caller must be a participant of the case. Otherwise the
answer is NOT_FOUND, never PERMISSION_DENIED, so the existence of a case is not revealed.
Organization admins have no special access to case content.

Metadata (number, kind, status, dates, participants) is plaintext so lists can be
rendered on the server. Everything descriptive (title, summary) is encrypted with the
case key in the browser.

| RPC | Request | Response | Description |
|---|---|---|---|
| `CreateCase` | `CreateCaseRequest` | `CreateCaseResponse` | Creates a case. The creator becomes its first conciliator and sends the case key already wrapped for their own public key. Errors: ALREADY_EXISTS (case number taken in the organization). |
| `GetCase` | `GetCaseRequest` | `GetCaseResponse` | Returns one case with the caller's role and wrapped case key. |
| `ListCases` | `ListCasesRequest` | `ListCasesResponse` | Lists the cases the caller participates in, newest activity first. |
| `UpdateCase` | `UpdateCaseRequest` | `UpdateCaseResponse` | Updates the encrypted descriptive fields or the schedule. Errors: ABORTED when `expected_revision` is stale. |
| `ChangeCaseStatus` | `ChangeCaseStatusRequest` | `ChangeCaseStatusResponse` | Changes the procedural status (open, in hearing, agreement, no agreement, archived). |
| `ListCaseEvents` | `ListCaseEventsRequest` | `ListCaseEventsResponse` | Returns the case activity timeline (metadata only, no content). |

### Service `ParticipantService`

People in a case and the distribution of the case key.

The server never holds the case key in clear: an existing participant wraps it for each
new participant's public key in the browser (GrantCaseKey).

| RPC | Request | Response | Description |
|---|---|---|---|
| `ListParticipants` | `ListParticipantsRequest` | `ListParticipantsResponse` | Lists the participants of a case. |
| `InviteParticipant` | `InviteParticipantRequest` | `InviteParticipantResponse` | Invites a person by email to the case. Only conciliators. If the person has no account yet, the invitation stays pending and the key is granted later. |
| `GrantCaseKey` | `GrantCaseKeyRequest` | `GrantCaseKeyResponse` | Wraps the case key for a participant who did not have it yet. Any participant who holds the key may do it, so access survives even if the conciliator is offline. |
| `ChangeParticipantRole` | `ChangeParticipantRoleRequest` | `ChangeParticipantRoleResponse` | Changes a participant's role. Only conciliators. The last conciliator cannot be demoted. |
| `RemoveParticipant` | `RemoveParticipantRequest` | `RemoveParticipantResponse` | Removes a participant. Only conciliators. Their wrapped key is deleted; content they already downloaded cannot be recalled (documented limitation of any E2E system). |

## `actaflow.collaboration.v1`

### Service `CollaborationService`

Real-time collaborative editing of a minute. Implemented by legal-case-service.

The minute is a CRDT document (Yjs). Every update is encrypted with the case key in the
browser; the server only orders, stores and relays ciphertext, so it cannot read the minute.

Two channels share these messages:
* this RPC service, used by the offline outbox to sync when there is no live connection;
* a WebSocket directly to legal-case-service (Vercel functions cannot keep long-lived
sockets). Its frames are ClientFrame and ServerFrame below, serialized as binary
protobuf, so the WebSocket is covered by the contract too.

No duplicated requests: every update has a client-generated UUID; the server stores it once
and acknowledges duplicates without relaying them again.

## `actaflow.engine.v1`

### Service `TranscriptionService`

The AI engine: speech-to-text and legal entity extraction, running on our own server.

Because of professional secrecy no audio or text is ever sent to third-party AI APIs.
The engine is below the gateway: only legal-case-service calls it, and every call is
signed (HMAC in the gRPC metadata). It also implements
actaflow.system.v1.ServiceStatusService and actaflow.crypto.v1.ProcessorKeyService.

Content arrives sealed for the engine (actaflow.crypto.v1.SealedEnvelope); the engine opens
it in memory, processes it and returns the result encrypted with the same content key.

## `actaflow.hearings.v1`

### Service `HearingService`

Live hearings: audio capture, transcription and entity extraction.
Implemented by legal-case-service, which queues the work for the AI engine.

Flow of the case study (3.3):
1. The browser captures the audio of each intervention in a Web Worker, splits it with
voice-activity detection and seals each segment for the AI engine.
2. SubmitAudioSegment stores the sealed segment and queues a transcription job. The engine
transcribes it and labels it with the speaker marked in the room.
3. When the hearing ends (or on demand), RequestEntityExtraction queues the extraction
over the corrected transcript.
4. ConfirmEntities stores what people confirmed; the minutes package then fills the template.

The API never waits for the AI: every heavy step is an asynchronous job.

|---|---|---|---|
| `StartHearing` | `StartHearingRequest` | `StartHearingResponse` | Starts a hearing in a case. Only conciliators. At most one hearing in progress per case. |
| `EndHearing` | `EndHearingRequest` | `EndHearingResponse` | Ends the hearing in progress. |

### Service `AuthService`

Zero-knowledge authentication with mandatory TOTP second factor.

The password never leaves the browser. From it the browser derives, with PBKDF2-SHA-256:
* an auth verifier, sent to the server and stored only as an HMAC-SHA-256 with a server secret;
* a separate key-encryption key that unlocks the user's private key kit locally.
Because the server only sees the verifier, it cannot decrypt anything.

Implemented by identity-service. Called only by the BFF, which keeps the tokens in
httpOnly cookies and never hands them to the browser's JavaScript.

| RPC | Request | Response | Description |
|---|---|---|---|
| `GetLoginParameters` | `GetLoginParametersRequest` | `GetLoginParametersResponse` | Returns the key-derivation parameters for an email. For unknown emails it returns deterministic fake parameters, so the answer never reveals whether an account exists. |
| `Register` | `RegisterRequest` | `RegisterResponse` | Creates an account from an invitation and starts the mandatory TOTP enrollment. Errors: FAILED_PRECONDITION (invalid, used or expired invitation), ALREADY_EXISTS (email taken). |
| `ConfirmTotpEnrollment` | `ConfirmTotpEnrollmentRequest` | `ConfirmTotpEnrollmentResponse` | Confirms TOTP enrollment with a first code. Returns the one-time recovery codes and the first session. Errors: UNAUTHENTICATED (wrong code), NOT_FOUND (unknown enrollment). |
| `Login` | `LoginRequest` | `LoginResponse` | First login step: checks the auth verifier and opens a short second-factor challenge. Errors: UNAUTHENTICATED (wrong credentials, always the same message), RESOURCE_EXHAUSTED (too many attempts). |

## `actaflow.jobs.v1`

### Service `JobService`

Asynchronous jobs (transcription, extraction, template filling, PDF and seal).
Implemented by legal-case-service.

The API never waits for heavy work. Workers take jobs from a PostgreSQL queue with
FOR UPDATE SKIP LOCKED, retry with exponential backoff, and only the job's own case
participants can read it.

| RPC | Request | Response | Description |
|---|---|---|---|
| `GetJob` | `GetJobRequest` | `GetJobResponse` | Returns one job. |
| `WatchJob` | `WatchJobRequest` | `stream WatchJobResponse` | Streams the job's state until it finishes (DONE or FAILED), then ends. |

## `actaflow.minutes.v1`

### Service `MinuteService`

Minutes (actas) and their final sealed documents. Implemented by legal-case-service.

Step 4 of the case study: "the AI autocompletes the official minute by pouring the extracted
data onto the selected legal template". Because the minute is confidential, no server fills it:
since v0.4.0 the browser fills the published template with the reviewed entities itself (the
template language is public and deterministic) and only the final content leaves it, sealed
for the AI engine, which renders the PDF (actaflow.engine.v1.DocumentService). legal-case
signs the PDF's SHA-256 without ever seeing the PDF. FillMinute is kept for compatibility but
legal-case answers UNIMPLEMENTED.

Legal note: the final document carries an INTEGRITY SEAL (SHA-256 + CMS signature with
ActaFlow's own certificate) plus each party's acceptance confirmed with their TOTP. It is
not a certified digital signature under Colombian Ley 527 de 1999, which requires a
certificate from an ONAC-accredited certification authority.

{{ partes.convocante.nombre }}                    variable
